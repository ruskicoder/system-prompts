# Complete Reverse Engineering of a CAPTCHA System

## Scenario
Goal: reverse a large CAPTCHA system to understand its complete operating principle and verification flow.

## Target entities
- **nc.js** (72KB): Webpack-bundled slider core (9 modules)
- **fireyejs.js** (583KB): DSL VM interpreter (custom instruction set with 26 opcodes)
- **awsc.js** (9KB): module loader
- **secaptcha.js** (72KB): WASM C build output (emscripten)
- **et_f.js** (262KB): another DSL VM type file

## Verified technical options

### Option A: Selenium + CDP drag (recommended)
Send native mouse events through CDP `Input.dispatchMouseEvent` and complete the verification in a real browser.
- Success rate: high
- Dependencies: Chrome + Selenium/Playwright

### Option B: Playwright headless browser runner
Load the DSL VM and module loader in Playwright and expose the token through an HTTP API.
- Success rate: medium (depends on the WASM initialization environment)

### Option C: pure requests protocol verification
Call the API endpoints directly through HTTP requests for verification.
- Success rate: **very low** (the token is tightly bound to the browser TLS/IP/fingerprint)
- Not recommended

## Key findings

1. **The token cannot be used outside the browser**: when a token generated by the DSL VM is submitted, the server checks context consistency (TLS JA3, IP, cookies, Referer and so on)

2. **fireyejs.js is not a WASM binary but a DSL VM**: a custom virtual machine implemented in 583KB of pure JS that runs encoded instructions in an interpreter loop with 26 opcodes

3. **The 9 modules of nc.js are 100% reversed**: including API endpoints, the slider UI, interaction logic, the ncSessionID algorithm, multilingual support and more

4. **The real WASM build output is secaptcha.js**: 72KB, uses SharedArrayBuffer + Atomics, C code compiled with emscripten

## Pitfall record

1. A test appkey does not trigger real verification; the appkey of the real page must be used
2. Only a specific status code returned by `initialize` means slider mode; `success` only confirms session creation
3. URL events of JSONP requests in the performance log may be captured incompletely because of how the script tags are injected
4. Exported function names do not exist in the DSL VM file (they are encoded by the VM); the real exports are exposed through the module registry

## Reusable patterns

- **DSL VM reverse engineering pattern**: `case extraction → opcode classification → constant table analysis → function tracing → export extraction`
- **General architecture of CAPTCHA systems**: `entry JS → module loader (WASM/DSL) → API communication layer → front-end UI → server-side verification`
- **Native CDP event bypass**: `Input.dispatchMouseEvent` bypasses detection and is unrelated to WebDriver

## Toolchain

- Selenium + CDP: browser automation + native mouse events
- Playwright: headless browser + route interception
- Python requests: pure API calls (verification failed)
- Node.js + Playwright: runner service
